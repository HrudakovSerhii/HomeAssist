# Road to v1.0 — Gap Analysis & Work Plan

Audit date: 2026-08-24. Base: `v1.1.0` (merge of `feature/emails-categorisation`, PR #5).

## What is already done (and works)

- Embedding-based email categorization (`Xenova/all-MiniLM-L6-v2`, 9 categories, precomputed
  category embeddings, cosine similarity) wired into the schedule processing path.
- Category-specific optimized prompt templates (~60–85 tokens) for small local models via Ollama.
- Content cleaning pipeline (HTML strip, signatures, URL simplification, truncation).
- Schedule engine on NestJS Scheduler (recurring cron + date-range), execution tracking,
  LLM availability check before a run, idempotent re-processing of failed emails.
- Dashboard with category badges, category filter, pagination, account info.
- IMAP fetch with `since`/`before` search criteria, 10-min socket timeout for batches.
- Credentials encrypted at rest (AES-256-GCM), passwords hashed with bcrypt.

## Blockers before testing on a real mailbox (Stage 0)

1. **No `.env.example` and no setup README.** All npm scripts require
   `.env.development` / `.env.test` / `.env.production`, but no file documents the required
   variables (`DATABASE_URL`, `LLM_OLLAMA_URL`, `LLM_DEFAULT_MODEL`, `APP_PASSWORD_ENCRYPTION_KEY`,
   `FRONTEND_URL`, `BACKEND_PORT`, `PROCESSING_MAX_EMAILS_PER_EXECUTION`, `INITIAL_LOOKBACK_DAYS`).
   → Add `.env.example` + a "run it locally" section in README (Postgres via
   `docker-compose.db.yml`, `db:migrate`, `ollama pull`, backend/frontend dev scripts).

2. **Insecure default encryption key.** `EncryptionService.getEncryptionKey()` falls back to
   `'default-key-change-in-production-32chars'` with a static `'salt'`. IMAP passwords stored
   with a publicly known key. → Fail fast at startup when `APP_PASSWORD_ENCRYPTION_KEY` is unset.

3. **LLM model is hard-coded to the config default (`mistral:latest`).**
   `processEmailWithEmbeddingClassification` calls `config().llm.defaultModel` directly
   (bypassing `ConfigService`), while `LOCAL-LLM-OPTIMIZATION.md` recommends `llama3.2:3b`.
   → Read model via `ConfigService`, align default with the docs, optionally allow per-schedule model.

## Pipeline correctness (Stage 1)

4. **Embedding classification result is not persisted.** The stored `category` comes only from
   the LLM's parsed JSON; on parse/validation failure it silently defaults to `PERSONAL`.
   The (cheap, reliable) embedding category + confidence is used only for template selection and
   then thrown away. → Persist `classification.category`/`confidence` (Prisma migration) and use
   it as the fallback instead of `PERSONAL`; decide reconciliation rule when LLM disagrees.

5. **Fragile JSON parsing from small models.** `parseLLMResponse` regex-extracts `{...}`,
   fakes `confidence: 0.8`, and falls back to a stub on failure. → Use Ollama's `format: 'json'`
   option, retry once with a stricter instruction on parse failure, keep real confidence.

6. **Known bug (tasks/issues/bugs.md):** failed IMAP credential test during account creation
   does not return an error to the client. → Fix + regression test.

7. **`since`/`before` TODOs in `email-ingestion.service.ts`** — parameters accepted but not
   forwarded, while `imap.service` already supports them. → Wire through; verify DATE_RANGE
   backfill end-to-end.

8. **Open question (tasks/issues/questions.md):** should editing an active schedule apply
   immediately? → Decide and implement (recommended: re-register cron job on update).
